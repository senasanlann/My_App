Kotlin Defterim

Görevlerim uygulamasını baştan kurarken öğrendiğim her Kotlin ve Android Compose kavramı, aşama aşama. Her terim: ne olduğu, nasıl kullanıldığı ve neden o şekilde yazıldığı. 1. Aşama'dan 28. Aşama'ya, ve ürünleşme sürecindeki gerçek hata hikâyelerini anlatan Ek'lere kadar.

01

Proje Kurulumu

Öğrendiğin: Version Catalog, Gradle eklentileri, KSP, Room/DataStore farkı
libs.versions.toml
Projedeki tüm kütüphane versiyonlarını tek yerde toplayan dosya. [versions] versiyon numaralarını, [libraries] kütüphaneleri, [plugins] eklentileri tanımlar. Tire (-) ile yazılan isimler, kodda nokta (.) ile erişilir: androidx-core-ktx → libs.androidx.core.ktx.
apply false
Kök build.gradle.kts'de bir eklentiyi apply false ile yazmak, "bu eklenti projede mevcut ama henüz hiçbir modülde aktif değil" demektir. Gerçek kullanım, modülün kendi build.gradle.kts'inde apply false yazmadan yapılır.
Benzetme: kök dosya bir kütüphane rafı ("bunlar mevcut"), modül dosyası senin masan ("bunu gerçekten kullanıyorum").
KSP (Kotlin Symbol Processing)
Kodundaki @Entity, @Dao gibi etiketleri (annotation) derleme sırasında tarayıp, arkasında gerçek çalışan kodu otomatik üreten araç. Room'un SQL'i senin yerine yazmasını sağlayan şey budur.
Room vs DataStore
Room: çoklu kayıt, tablo yapısı, güçlü sorgu (arama/filtre/sıralama) gerektiren veriler için (kullanıcılar, görevler). DataStore: tek, basit anahtar-değer bilgisi için (örn. "oturum açık mı, hangi kullanıcı").
material-icons-extended
Compose BOM ailesinden olduğu için version.ref gerektirmeyen tek kütüphane örneklerinden biri — versiyonu zaten compose-bom'dan geliyor.
Paket yapısı (data / ui / model / navigation / util)
Kodu işlevine göre klasörlere ayırmak. data: veritabanı/repository, ui: ekranlar, model: sabit veri tipleri (enum'lar), navigation: ekran geçişleri, util: tekrar kullanılan yardımcı fonksiyonlar.
02

Veri Modelleri

Öğrendiğin: enum class, enum'a özellik eklemek, data class, annotation'lar
enum class
Sabit, önceden belirli birkaç seçenekten biri olabilen tip (örn. bir görev sadece TODO/IN_PROGRESS/DONE olabilir, başka bir şey olamaz). Düz String kullanmaktan farkı: yazım hatası derleme anında yakalanır.
enum'a özellik eklemek
Her enum değerinin kendi ek verileri (yazı, renk, sayı) olabilir — tıpkı bir class constructor'ı gibi.
enum class TaskPriority(val displayName: String, val level: Int) {
    LOW(displayName = "Düşük", level = 1),
    HIGH(displayName = "Yüksek", level = 3)
}
data class
Sadece veri taşımak için kullanılan class — bir "satır/kayıt" temsil eder. Kotlin otomatik olarak karşılaştırma, kopyalama (.copy()) gibi işlevler kazandırır.
@Entity
Bir data class'ın Room için "bu bir veritabanı tablosu" olduğunu belirten etiket. tableName ile tablo adı verilir.
@PrimaryKey(autoGenerate = true)
Her satırı ayırt eden benzersiz kimlik. autoGenerate ile Room, id'yi otomatik ve artan şekilde kendisi üretir.
Index(unique = true)
Bir sütunda tekrar olamayacağını veritabanı seviyesinde zorunlu kılar (örn. aynı email iki kez kayıt olamaz).
ForeignKey + onDelete = CASCADE
Bir sütunun başka bir tablodaki gerçek bir kayda bağlı olmasını zorunlu kılar. CASCADE: bağlı olunan satır silinirse, ona bağlı satırlar da otomatik silinir.
03

Veritabanı Kurulumu

Öğrendiğin: Room, DAO, suspend fonksiyonlar, Flow, singleton
@Dao / interface
Veritabanı işlemlerini tanımlayan, gövdesiz bir sözleşme. interface çünkü gerçek SQL kodunu KSP arkada üretir, biz sadece imzayı yazarız.
@Insert / @Query
@Insert: verilen nesneyi otomatik SQL ile ekler. @Query("..."): kendi SQL'ini yazarsın, :parametre ile fonksiyon parametresine bağlanır.
suspend fun
"Bu işlem zaman alabilir, çağırırken ana ekranı (UI thread) dondurma" demek. Tüm veritabanı okuma/yazma fonksiyonları (tek seferlik sonuç dönenler) suspend olmalı.
Flow<T>
Tek seferlik sonuç değil, canlı akış. İlgili veri değiştiğinde otomatik yeni değer gönderir — ekranı elle yenilemeye gerek kalmaz. Listeleme sorgularında suspend olmadan kullanılır.
@Database
Tüm tabloları (entity'leri) ve DAO'ları bir araya getiren merkezi sınıf. entities = [...], version, exportSchema = false parametreleri alır.
Singleton + companion object
Uygulama boyunca veritabanının sadece 1 nesnesi olmasını garanti eden desen. companion object, bir class'a ait ama örnek oluşturmadan çağrılabilen fonksiyonlar barındırır (AppDatabase.getInstance(...)).
companion object {
    @Volatile private var INSTANCE: AppDatabase? = null
    fun getInstance(context: Context): AppDatabase =
        INSTANCE ?: synchronized(this) {
            Room.databaseBuilder(context.applicationContext,
                AppDatabase::class.java, "app_database")
                .build().also { INSTANCE = it }
        }
}
Application sınıfı + manifest kaydı
Herhangi bir ekrandan önce, uygulama açılışında bir kez çalışan nesne. AndroidManifest.xml'de android:name=".GorevlerimApp" ile kaydedilmezse Android bu sınıfı hiç kullanmaz.
lateinit var ... private set
lateinit: "şimdi değer veremem ama kullanılmadan önce atayacağım" sözü. private set: değişken dışarıdan okunabilir ama sadece sınıfın kendisi tarafından değiştirilebilir.
04

Navigation İskeleti

Öğrendiğin: sealed class, NavHost, route, back stack
sealed class Screen
Tüm ekranların route'larını (adreslerini) tek yerde toplar. sealed, bu class'tan sadece aynı dosyada tanımlı türlerin türeyebileceğini garanti eder — yazım hatasını derleme anında yakalar.
sealed class Screen(val route: String) {
    object Login : Screen("login")
    object Register : Screen("register")
}
NavHost / rememberNavController
NavHost, ekranların gösterildiği konteyner (aynı anda sadece 1 ekran görünür). rememberNavController(), geçişleri yöneten "kumanda" — "şu ekrana git" komutlarını verir.
startDestination
Uygulama ilk açıldığında gösterilecek ekran. Gerçek mantık (örn. oturum kontrolü) hazır olana kadar geçici bir ekran seçilebilir.
Ekrana callback (lambda) parametre geçmek
Bir ekran "ne olacağını" bilmez, çağıran taraf (NavHost) söyler: LoginScreen(onNavigateToRegister = { navController.navigate(...) }). Ekranı test edilebilir ve yeniden kullanılabilir tutar.
Back stack + popBackStack()
Ziyaret edilen ekranlar üst üste dizilir, en üstteki görünen ekrandır. navigate() yığına ekler; popBackStack() en üsttekini kaldırıp altındaki (zaten var olan) ekrana döner — yeni kopya oluşturmaz.
Pratik ders (bugün bulundu): Scaffold kullanmayan bir ekranın içeriği durum çubuğunun (status bar) altına kadar çizilir. Sistem, ekranın en üst ~174 pikselini "zorunlu sistem hareketi" bölgesi sayar — oradaki butonlara dokunuşlar bazen uygulamaya değil sisteme gider. Çözüm: her ekranı Scaffold ile sarmalamak, innerPadding'i içeriğe uygulamak.

Kayıt Ekranı Arayüzü

Öğrendiğin: Column, Scaffold, OutlinedTextField, remember, mutableStateOf
Column / Scaffold
Column: elemanları üstten aşağıya sırayla dizer. Scaffold: ekranın standart iskeleti, içine koyduğun şey "doldurulacak" alana yerleşir.
mutableStateOf + remember
mutableStateOf(""): değiştiğinde Compose'u otomatik haberdar eden bir kutu. remember { }: bu kutuyu her yeniden çizimde (recomposition) sıfırlamadan, aynısını korur.
var name by remember { mutableStateOf("") }

OutlinedTextField(
    value = name,
    onValueChange = { name = it },
    label = { Text("Ad") }
)
by (property delegation)
mutableStateOf normalde .value ile okunur/yazılır. by kelimesi bu zahmeti kaldırır, direkt name yazarak okuyup değiştirebilirsin.
keyboardOptions (Email / Password)
Klavyenin alana göre şekil değiştirmesi — email'de @ kolay erişilir, şifrede otomatik büyük harf yapılmaz. Doğrulama yapmaz, sadece kullanıcı deneyimi kolaylığıdır.
visualTransformation
Ekranda ne göründüğünü değiştirir, gerçek veriyi değiştirmez. Şifreyi nokta (•) göstermek buna örnek — arkadaki gerçek değer aynen durur.
trailingIcon + IconButton
Bir kutunun sağına tıklanabilir ikon koymak (göz ikonu gibi). Tıklanınca bir boolean state'i tersine çevirip (!passwordVisible) görünümü değiştirir.
Button vs TextButton
Button: ana aksiyon, dolgulu/belirgin. TextButton: ikincil aksiyon, arka plansız/sade.

Kayıt ViewModel ve State

Öğrendiğin: ViewModel, StateFlow, copy(), tek yönlü veri akışı
data class UiState
Ekranın tüm durumunu (alanlar, hatalar, yükleniyor mu, başarılı mı) tek bir nesnede toplamak — dağınık onlarca remember değişkeni yerine tek kaynak.
ViewModel
Ekran döndürüldüğünde/yeniden oluşturulduğunda hayatta kalan özel sınıf. İş mantığı burada yaşar, UI'da değil.
MutableStateFlow + _x / x deseni
Her zaman güncel bir değeri olan akış. _uiState (private, değiştirilebilir) / uiState (public, sadece okunabilir — asStateFlow()) ayrımıyla, değiştirme yetkisi sadece ViewModel'de kalır.
private val _uiState = MutableStateFlow(RegisterUiState())
val uiState: StateFlow<RegisterUiState> = _uiState.asStateFlow()

fun onNameChange(newName: String) {
    _uiState.value = _uiState.value.copy(name = newName)
}
.copy()
Her data class'ın otomatik kazandığı fonksiyon — bir nesnenin birebir kopyasını, sadece belirttiğin alanı değiştirerek oluşturur. val (değiştirilemez) alanları güncellemenin yolu budur.
Tek yönlü veri akışı
Ekran → olay bildirir (onNameChange) → ViewModel state'i günceller → güncel state ekrana akar. Ekran state'i asla doğrudan değiştirmez.
ViewModelProvider.Factory
ViewModel'in constructor'ı parametre (örn. repository) istiyorsa, Android'e "onu ben şöyle kuracağım" diyen bir tarif yazman gerekir.
viewModel(factory = ...) + LocalContext.current
Compose'da bir ekrana ViewModel bağlamanın yolu. LocalContext.current, Compose'da Android Context'ine ulaşmanın özel yolu.
collectAsStateWithLifecycle()
Bir StateFlow'u Compose'un okuyabileceği hale getirir, ekran görünür değilken dinlemeyi otomatik durdurup kaynak tasarrufu sağlar.
07

Kayıt Formu Doğrulama

Öğrendiğin: Nullable tipler (String?), if/when, isBlank(), regex
object Validators
Kendine özel veri tutmayan, tekrar kullanılacak fonksiyonlar tek bir object'te toplanır — her yerden Validators.validateName(...) diye çağrılır.
String? dönüş tipi — "hata ya da yok" deseni
null = geçerli, hata yok. Dolu string = hata mesajı. Bu dil, UiState'teki ...Error alanlarıyla birebir uyumlu.
fun validateName(name: String): String? {
    if (name.isBlank()) return "Ad boş olamaz"
    if (name.length < 2) return "Ad en az 2 karakter olmalı"
    return null
}
isBlank()
Bir metnin boş VEYA sadece boşluk karakterlerinden oluşup oluşmadığını kontrol eder — kullanıcı sadece boşluk yazarak kuralı aşamaz.
Erken dönüş (early return)
Kurallar sırayla kontrol edilir, ilk uyan kuralda return ile hemen çıkılır.
Regex / Patterns.EMAIL_ADDRESS
Bir metnin belirli bir kalıba uyup uymadığını kontrol eden desen dili. Android'in hazır Patterns.EMAIL_ADDRESS kalıbıyla, kendimiz regex yazmadan email formatını kontrol ettik.
Tüm hataları toplayıp tek .copy() ile yazmak
validateForm(), 4 kontrolü çalıştırıp sonuçları önce değişkenlerde toplar, sonra tek bir .copy() ile state'e yazar — kullanıcı tüm hataları bir kerede görür, gereksiz çoklu güncelleme olmaz.
&& (VE) operatörü
"Hepsi doğru olursa sonuç doğru." Tüm hata alanlarının null olup olmadığını tek seferde kontrol etmek için kullanıldı.
isError + supportingText
OutlinedTextField'ın hazır parametreleri: isError = true çerçeveyi otomatik kırmızı yapar; supportingText alanın altına hata mesajını yerleştirir.
!! (çift ünlem)
"Buna güven, null değil" demenin yolu — sadece zaten null kontrolü yapılmış bir bloğun içinde güvenli kullanılır.
Değersiz return + doğrulama kapısı
Dönüş tipi olmayan (Unit) bir fonksiyonda tek başına return, sadece fonksiyondan çıkar. onRegisterClick()'te if (!isValid) return ile geçersiz form hiç kaydedilme aşamasına geçemez.

Kaydı Veritabanına Bağlama

Öğrendiğin: Repository deseni, viewModelScope.launch, coroutine, Result, @Transaction
SHA-256 / MessageDigest
Tek yönlü şifreleme algoritması — bir metni sabit uzunlukta, geri döndürülemez bir çıktıya çevirir. Aynı girdi her zaman aynı çıktıyı üretir, bu yüzden "şifre doğru mu" kontrolü tekrar hash'leyip karşılaştırarak yapılır.
object HashUtils {
    fun sha256(input: String): String {
        val bytes = MessageDigest.getInstance("SHA-256")
            .digest(input.toByteArray())
        return bytes.joinToString("") { "%02x".format(it) }
    }
}
Repository deseni
ViewModel, veritabanını (Room/DAO) doğrudan bilmez — sadece authRepository.register(...) gibi tek bir fonksiyon çağırır. İleride veri saklama şekli değişse bile (örn. bir API'ye geçilse), sadece Repository değişir, ViewModel etkilenmez.
Result<T> — success / failure
Bir işlemin başarılı mı başarısız mı olduğunu, başarısızsa sebebiyle birlikte taşıyan hazır Kotlin tipi. Result.success(Unit) / Result.failure(Exception("...")).
@Transaction / database.withTransaction { }
Birden fazla veritabanı işlemini "ya hep ya hiç" kuralıyla gruplar. İçindeki her şey ya tamamen başarılı olur ya da biri başarısız olursa hepsi otomatik geri alınır — yarım kayıt diye bir şey olmaz.
suspend fun register(...): Result<Unit> {
    return database.withTransaction {
        if (userDao.getUserByEmail(email) != null) {
            return@withTransaction Result.failure(Exception("Bu e-posta zaten kayıtlı"))
        }
        val id = userDao.insertUser(UserEntity(...))
        categoryDao.insertCategories(defaultCategories(id))
        Result.success(Unit)
    }
}
return@label (etiketli return)
İç içe lambda'larda, hangi lambda'dan çıkılacağını netleştirir: return@withTransaction sadece o bloktan çıkar, dıştaki fonksiyonu etkilemez.
coroutine + viewModelScope.launch
Arka planda, ana ekranı dondurmadan çalışan iş parçası. viewModelScope, bu işin ömrünü ViewModel'in ömrüne bağlar — ViewModel yok olursa iş otomatik iptal edilir.
result.onSuccess { } .onFailure { }
Result'un hazır fonksiyonları — sadece ilgili durumda çalışırlar, ikisi asla birden çalışmaz. Zincirlenebilirler çünkü her biri orijinal Result'ı aynen geri döndürür.
enabled = !uiState.isLoading
Yükleniyorken butonu tıklanamaz yapar — kullanıcının art arda basıp aynı kaydı birden fazla kez göndermesini engeller.
LaunchedEffect(key) { }
Composable gövdesi her yeniden çizimde çalışır; navigasyon/Toast gibi "bir kerelik" işleri doğrudan oraya yazamayız. LaunchedEffect, içindeki kodu sadece key değiştiğinde çalıştırır.
MaterialTheme.colorScheme.error / onPrimary
Temadan alınan anlamsal renkler — hata metni için error, buton rengi üzerinde okunabilir içerik için onPrimary. Elle renk kodu yazmak yerine temadan almak, koyu modda da otomatik doğru görünmesini sağlar.
Kayıt akışı uçtan uca çalışıyor: form → doğrulama → hash → transaction → Room. Aynı email ile ikinci kayıt denemesi doğru şekilde reddediliyor, yeni kullanıcıya 4 varsayılan kategori otomatik atanıyor.

Giriş Ekranı

Öğrendiğin: kodun yeniden kullanımı — yeni kavramdan çok, öğrenilenleri doğru yerde tekrar uygulamak
LoginUiState / LoginViewModel
RegisterUiState / RegisterViewModel'in birebir aynı iskeleti — data class + MutableStateFlow + _x/x deseni + Factory. Tek fark: daha az alan (sadece email, şifre).
Validators.validateEmail(...) — aynen tekrar kullanmak
59. adımda yazılan email format kontrolü, hiç değiştirilmeden hem Register'da hem Login'de çağrılıyor — kuralı iki kere yazmaya gerek kalmadı.
validatePassword(...)'ü BİLEREK kullanmamak
Login'de şifre için sadece isBlank() kontrolü var, 6 karakter kuralı (validatePassword) kullanılmıyor — çünkü girişte amaç "kurallara uygun mu" değil "bir şey yazıldı mı"; şifrenin doğruluğu zaten hash karşılaştırmasıyla anlaşılacak.
Ders: kodu tekrar kullanmak, her zaman aynı fonksiyonu çağırmak demek değil — doğru aracı doğru yerde seçmek demek.
suspend fun login(email: String, passwordHash: String): Result<UserEntity> {
    val user = userDao.getUserByEmail(email)
        ?: return Result.failure(Exception("E-posta veya şifre hatalı"))

    if (user.passwordHash != passwordHash) {
        return Result.failure(Exception("E-posta veya şifre hatalı"))
    }
    return Result.success(user)
}
?: return ... (Elvis + erken çıkış)
32. adımda INSTANCE ?: synchronized(...) ile gördüğümüz Elvis operatörünün farklı bir kullanımı: "sol taraf null ise, sağdakini çalıştırıp fonksiyondan hemen çık." if (x == null) { return ... } yazmanın kısa yolu.
Result<UserEntity> — neden Result<Unit> değil
register()'da başarı durumunda dönecek anlamlı veri yoktu. Girişte ise başarılı olursa kullanıcının gerçek bilgilerine (id, email, ad) ihtiyaç var — ileride oturum bilgisini saklarken kullanılacak.
Aynı hata mesajı, iki farklı sebep — güvenlik
"Kullanıcı bulunamadı" ile "şifre yanlış" durumlarında bilerek aynı "E-posta veya şifre hatalı" mesajı gösteriliyor.
Neden: farklı mesajlar olsaydı, biri Login formunu deneme-yanılma ile kullanarak hangi email'lerin sistemde kayıtlı olduğunu öğrenebilirdi (user enumeration saldırısı). Belirsiz mesaj, bu bilgiyi hiç sızdırmıyor.
onLoginClick() — register akışının aynısı
doğrula → isLoading = true → viewModelScope.launch → hash'le → repository çağır → onSuccess/onFailure. 74-75. adımlardaki onRegisterClick() ile yapısal olarak birebir aynı.

Oturum Yönetimi

Öğrendiğin: DataStore, Flow.map, extension property
Extension property (uzantı özelliği)
Kendi yazmadığın, başkasına ait bir sınıfa (örn. Android'in Context'i) dışarıdan yeni bir özellik "yapıştırma" yolu. Bir kere tanımlayınca, projenin her yerinde o sınıfın normal bir üyesiymiş gibi kullanılır.
val Context.dataStore by preferencesDataStore(name = "session_prefs")

// artık her yerde:
context.dataStore
preferencesDataStore(name = "...")
DataStore kütüphanesinin hazır fonksiyonu — verilen isimde bir dosyada anahtar-değer verisi saklayan bir DataStore nesnesi oluşturur/döndürür. Tıpkı Room'daki singleton gibi, dosya başına tek örnek olmalı — bu yüzden class'ın değil, dosyanın en üstünde tanımlanır.
Tipli anahtarlar (Key)
DataStore'a düz string ile değil, longPreferencesKey("user_id") / stringPreferencesKey("user_name") gibi tipli anahtarlarla yazılır. Bu, "bu anahtarın değeri mutlaka şu tip olmalı" garantisini derleme anında verir.
suspend fun saveSession(userId: Long, name: String, email: String) {
    context.dataStore.edit { preferences ->
        preferences[USER_ID] = userId
        preferences[USER_NAME] = name
        preferences[USER_EMAIL] = email
    }
}
.edit { preferences -> ... }
DataStore'a yazmanın yolu. Lambda'nın içindeki tüm atamalar tek bir atomik işlem olarak diske yazılır — @Transaction'daki "ya hep ya hiç" ruhuna benzer. Okuma için ise DataStore kendi hazır bir Flow sağlar: context.dataStore.data — tüm kayıtlı verinin canlı akışı.
Flow.map { }
Bir Flow'un yayınladığı her değeri başka bir şeye dönüştüren araç — listelerdeki .map'in, zamanla akan bir veri üzerindeki karşılığı. .data bize tüm Preferences blobunu veriyordu; .map ile içinden sadece ilgilendiğimiz tek alanı çekiyoruz.
val userIdFlow: Flow<Long?> = context.dataStore.data.map { preferences ->
    preferences[USER_ID]
}
Neden nullable (Long?, String?)
Kullanıcı hiç giriş yapmadıysa, o anahtar DataStore'da hiç yazılmamıştır — preferences[USER_ID] otomatik olarak null döner. "Oturum yok" bilgisini, fazladan bir kontrol yazmadan, doğal olarak elde ediyoruz.
preferences.clear()
Tüm kayıtlı anahtarları tek seferde siler — çıkış (logout) yaparken tek tek anahtar silmek yerine kullanılan en basit yol.
popUpTo(route) { inclusive = true }
Bir ekrana navigate() ederken, aynı zamanda back stack'i belirli bir noktaya kadar temizlemenin yolu. popUpTo(Screen.Login.route): "Login route'una kadar her şeyi yığından sil." inclusive = true: "Login'in kendisi de dahil, o da silinsin." Bir class'ın oluşturulduğu an, kimse çağırmadan, otomatik olarak bir kere çalışan blok. Fonksiyonlardan farkı: fonksiyonlar sen çağırınca çalışır, init nesne var olur olmaz kendiliğinden tetiklenir. Oturum kontrolünü ViewModel oluşur oluşmaz başlatmak için kullanıldı.

Durum yönetimi — neden 3 durumlu bir enum

Öğrendiğin: sortedBy, compareBy + thenBy, Collator
sortedBy / sortedByDescending / sortedWith
Kotlin'in hazır sıralama fonksiyonları. sortedBy { it.createdAt } küçükten büyüğe, sortedByDescending tersi sıralar. Daha karmaşık kurallar (örneğin "önce şuna göre, eşitse buna göre") için sortedWith(comparator) kullanılır.

Bir Comparator'a zincirleme ikinci bir kural eklemenin yolu. titleComparator.thenByDescending { it.createdAt }: önce başlığa göre sırala, başlıklar eşitse en yeniyi öne al. Bu sayede sıralama sonucu her zaman öngörülebilir (belirsiz/rastgele sırada eşit eleman kalmaz).

strings.xml ve neden önemli
Önceden hata mesajları ("Ad boş olamaz" gibi) doğrudan Kotlin kodunun içinde yazılıydı. res/values/strings.xml'e taşınınca: (1) aynı metin birden fazla yerde tekrar yazılmaz, (2) ileride başka bir dile çevirmek istenirse sadece bu dosyanın bir kopyası (values-en/strings.xml gibi) yeterli olur, (3) Android Studio'nun metin araçları (arama, kullanılmayanı bulma) çalışabilir.

Ekranda gerçek metne çevirmek için Composable içinde stringResource(id) çağrılır.

    ...
}

// RegisterScreen.kt
supportingText = {

LocalFocusManager.current, kodla "hangi alan odakta" kontrolünü sağlar. Uzun formlarda (Kayıt Ol gibi) klavye açılınca alt butonlar ekran dışına taşabilir. Modifier.verticalScroll(rememberScrollState()).imePadding() ikilisi: formu kaydırılabilir yapar (verticalScroll) ve klavye açıldığında içeriği klavyenin üstünde kalacak kadar yukarı iter (imePadding).

Yani "İş".lowercase() beklediğimiz "iş" değildi, bu yüzden "İş" kategorisi kendi "iş" anahtar kelimesiyle eşleşmiyordu. Çözüm: name.lowercase(Locale("tr")) — Türkçe'ye özel kurallarla küçültme.

2) Alt-dize (substring) tuzağı: "Kişisel" ve "Alışveriş" kelimelerinin içinde, anlamsal olarak hiç ilgisi olmadığı hâlde, harfler tesadüfen yan yana gelip "iş" alt-dizesini oluşturuyordu (k-i-ş-i-s-e-l → "iş" pozisyon 1-2'de var!). lower.contains(keyword) bunu da eşleşme sayıyordu. Çözüm: Alt-dize yerine kelimeyi boşluk/noktalama işaretlerinden ayırıp tam kelime eşleşmesi aranması (words.any { it == keyword }).

Bu iki hata da ADB ile ekran görüntüsü alınarak (önce yanlış ikonlar fark edildi) ve kodu adım adım yeniden okuyarak bulundu — bir string fonksiyonunun "aşikâr" davranışının, Türkçe gibi özel alfabeler söz konusu olunca aslında hiç aşikâr olmayabileceğinin iyi bir örneği.

Photo Picker (ActivityResultContracts.PickVisualMedia)

@Composable
fun rememberImagePickerLauncher(onImagePicked: (Uri) -> Unit): () -> Unit {
    val launcher = rememberLauncherForActivityResult(
        contract = ActivityResultContracts.PickVisualMedia()
    ) { uri -> if (uri != null) onImagePicked(uri) }

    return { launcher.launch(PickVisualMediaRequest(...ImageOnly)) }
}

Seçilen dosyayı kendi alanımıza kopyalamak
Galerinin verdiği content:// adresi (Uri) her zaman kalıcı/güvenilir olmayabilir. util/ImageStorage.kt, dosyanın baytlarını okuyup uygulamanın kendi özel klasörüne (filesDir/images/) kopyalıyor ve bu yeni, kalıcı dosya yolunu (düz bir String) döndürüyor — Room'da saklanan da bu yol.
suspend fun save(context: Context, uri: Uri, prefix: String): String =
    withContext(Dispatchers.IO) {
        val file = File(File(context.filesDir, "images").apply { mkdirs() }, "$prefix_${'$'}{UUID.randomUUID()}.jpg")
        context.contentResolver.openInputStream(uri)?.use { input ->
            file.outputStream().use { output -> input.copyTo(output) }
        }
        file.absolutePath
    }

Kök neden: Hangi kategoride olduğumuzu tutan değişken, remember { mutableStateOf(...) } ile ekranın geçici state'inde tutuluyordu. Navigation-Compose'da bir ekranın üstüne yeni bir ekran (AddEditTaskScreen) açılıp geri dönüldüğünde, alttaki ekranın composable fonksiyonu yeniden baştan çalışır — remember ile tutulan her şey sıfırlanır. Oysa aynı ekranın ViewModel'i (ve ona bağlı filterState) hayatta kalır, çünkü ViewModel'in ömrü composable'ın değil, navigasyon kaydının (NavBackStackEntry) ömrüne bağlıdır.

İlk (yanlış) düzeltme: Paylaşılan bir "sinyal" (AppContainer'da tutulan, tüketilince null'a çekilen bir state) ile bu bilgiyi aktarmayı denedim — ama tüketme işleminin kendisi yeni bir "sinyal yok" olayı üretip, ekranın az önce doğru okuduğu değeri bu sefer kendi kendine siliyordu.

Doğru çözüm: Ayrı bir "hangi kategorideyiz" değişkenini tamamen kaldırıp, başlığı doğrudan zaten kalıcı olan veriden türetmek: uiState.filterState.categoryId ile uiState.categories listesinden kategori adını bulmak. Aynı kaynak, filtre çipinde zaten kullanılıyordu — artık başlık da ondan geliyor. 
// Önce: ayrı, kırılgan bir "hangi kategorideyiz" state'i
var remember { mutableStateOf<Pair<Long,String>?>(null) }

// Sonra: zaten kalıcı olan ViewModel verisinden türetilmiş
val activeCategory = uiState.filterState.categoryId
    ?.let { id -> uiState.categories.firstOrNull { it.id == id } }
Ders: Bir navigasyon geçişinden (özellikle üstüne yeni ekran açılıp kapanmasından) sağ salim çıkması gereken bilgiyi, ekranın geçici remember state'inde değil, ViewModel'de (ya da ondan türetilebilir bir yerde) tutmak gerekir. "Nereden geldiğimizi hatırlamak için ayrı bir değişken" ihtiyacı duyulduğunda, önce "zaten elimde olan veriden bu çıkarılabilir mi?" diye sormak, yeni bir senkronizasyon sorunu yaratmaktan çok daha sağlam.
